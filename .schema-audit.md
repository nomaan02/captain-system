# QuestDB Schema Audit — Session A

**Date:** 2026-04-20
**Scope:** Full read-only inventory of every QuestDB table used by
captain-offline, captain-online, and captain-command, plus shared/ and
scripts/. Produces `shared/canonical_schemas.py` as the single source of
truth for a fresh-start bootstrap on both towers (no migration).
**QuestDB version:** 9.3.3.

## Method

1. Treated `scripts/init_questdb.py` (818 lines, 39 CREATE TABLEs) as
   the *claimed* schema.
2. Treated `scripts/compact_questdb_tables.py` (253 lines, 5 DDLs for
   D01/D02/D05/D12/D25) as a second claimed schema that runs every 48h
   on the tower; compared it column-by-column with init.
3. Harvested every `INSERT INTO p3_*`, `SELECT ... FROM p3_*`, and
   `LATEST ON ... PARTITION BY ...` across the three services + shared/
   + scripts/ — ~180 call sites total.
4. For each table, cross-referenced: claimed DDL (init), claimed DDL
   (compact), columns actually written, columns actually read, the
   natural key implied by LATEST ON usage, the timestamp column used for
   the designated timestamp.
5. Checked for runtime DDL (ALTER / CREATE / DROP) in application code.
   Result: zero — only scripts/init_questdb.py, compact_questdb_tables.py,
   and init_sqlite.py issue DDL. SQLite CREATE TABLEs in
   shared/journal.py and shared/bar_cache.py are unrelated to QuestDB.

### B. Should-fix (DDL correctness — no observed live failure, but fresh install is our chance to get it right)

| ID | Table(s) | Problem | Resolution |
|---|---|---|---|
| B-1 | D00, D01, D02, D04, D05, D06b, D07, D08, D12, D13, D14, D15, D16, D17, D23, D25, D26, offline_job_queue | **No PARTITION BY** in init_questdb.py. `captain-command/captain_command/`, `shared/` for `CREATE TABLE`, `ALTER TABLE`,

- `scripts/init_sqlite.py` — SQLite journals, out of scope

No production block issues schema changes at runtime. Safe to replace the
DDL source of truth by swapping init_questdb.py over to import from
`shared.canonical_schemas.CANONICAL_DDLS` in a follow-up session.

## Ingestion mode check

All writes go through psycopg2 / PG wire protocol (`shared/questdb_client.py`
`get_cursor()` + `cur.execute("INSERT INTO ...")`). Zero uses of QuestDB's
ILP `Sender`, zero `.send()` calls, zero WAL-file writers. This is why
WAL + DEDUP on the DDL side is safe to add — it changes the table's
storage engine, not the client protocol.

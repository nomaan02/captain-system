## 2. Scheduling — complete picture

### Container-level schedules

**None.** Verified by zero matches for `BackgroundScheduler`, `AsyncIOScheduler`, `scheduler.add_job`, `scheduled_job`, `CronTrigger`, `IntervalTrigger`, `asyncio.sleep`, `asyncio.create_task` across the Python codebase.

No container periodically writes to any QuestDB table — the original audit's "no periodic schedulers" finding holds. All writes to D29–D33 and spread_history are event-driven (OR resolution, feature computation cycle).

### Host-level schedules (both towers, user-owned crontabs)

Three cron entries per tower, all targeting filesystem data — **none of them write to QuestDB directly**:


| #   | Schedule       | Target                                                        | What it does                                                                                                             | Touches QuestDB?                                                          |
| --- | -------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| 1   | `0 22 * * 1-5` | `~/captain-system/scripts/update_vix_data.sh`                 | Downloads raw VIX & VIX3M CSVs from CBOE, converts to `data/vix/vix_daily_close.csv` and `data/vix/vxv_daily_close.csv`. | No — writes to filesystem CSVs.                                           |
| 2   | `*/5 * * * `*  | `~/healthcheck.sh`                                            | Container health monitoring. Logs to `~/captain-system/logs/healthcheck.log`.                                            | Unknown (script contents not inventoried; no evidence of QuestDB writes). |
| 3   | `0 2 * * *`    | Inline `tar czf` → `~/backups/questdb-$(date +%Y%m%d).tar.gz` | Snapshots `questdb/db/` with 14-day retention.                                                                           | Reads raw QuestDB files; does not write.                                  |


**Why this matters for the seed audit:** The VIX cron is the only cron that touches data the live pipeline consumes. AIM-04 (`aim_feature_loader.py:115`, `b1_features.py:591`) and AIM-11 read `vix_daily_close.csv` and `vxv_daily_close.csv` at runtime and compute IVTS live (`f["ivts"] = vix_close / vxv_close`). If the VIX cron is paused, disabled, or silently failing, regime features degrade to a stale snapshot of the last successful run. This dependency was not captured in the original audit.

No systemd timers. No root crontab.

## 3. Defects & corrections surfaced by the investigation

### Defect 1 — VIX cron log path typo (Tower 1 only) — **FIXED**

`crontab -l` pointed at `/home/captain-system/logs/vix_update.log` (missing `nomaan/` prefix). Output was silently discarded for the life of the install. Fixed in-session by editing crontab to `/home/nomaan/captain-system/logs/vix_update.log`. Tower 2 was installed by `tower-deploy.sh (2026-04-13)` with the correct `/home/isaac/...` path from day one.

### Defect 2 — VIX installer script out of sync with reality — **OPEN**

`deploy/install-vix-cron.sh` installs `update-vix-data.sh` (hyphens) into `/home/captain/`. Real crontab points at `update_vix_data.sh` (underscores) in `/home/$USER/captain-system/scripts/`. The installer was either superseded by hand-editing or was written for a different deployment layout. **Not urgent for trading**; must be resolved before the next fresh install to avoid re-introducing Defect 1.

### Defect 3 — VIX script `echo` output is mangled — **COSMETIC, LOW PRIORITY**

Final line of `update_vix_data.sh`:

```bash
echo "$(date): VIX/VXV updated. VIX last: $(tail -1 $DIR/vix_daily_close.csv), VXV last: $(tail -1 $DIR/vxv_daily_close.csv)"

```

Both `tail -1` substitutions include trailing newlines which reorder the final string. Data lands correctly in the CSVs regardless (verified: Tower 1 `vix_daily_close.csv` contains clean `2026-04-20,18.87` row). One-line fix available (`tail -1 file | tr -d '\n'`); apply opportunistically.

### Defect 4 — D01 compaction bug on non-partitioned table — **RESOLVED BY FRESH-START**

D01 is non-partitioned in the current production DDL. Compaction re-inserts rows in key order, violating QuestDB's non-partitioned timestamp-order constraint. On the most recent `captain-start` on Tower 2 this truncated 272 logical rows to 20 (~252 cold-start state rows lost — no trained models). The fresh-start branch adds `PARTITION BY MONTH` to D01, eliminating the constraint. No action required beyond verifying the fresh DDL is applied on both towers.

### Defect 5 — `ivts_daily.csv` is legacy / unmaintained — **NO ACTION REQUIRED**

Both towers have `data/vix/ivts_daily.csv` last-written 2026-03-21. The VIX cron **does not produce this file** (the original audit implied it did; this was incorrect). `grep -rn "ivts" shared/ captain-online/ captain-offline/` confirms no code path reads `ivts_daily.csv` — it is a research artefact. Live IVTS is computed at runtime from the `_close.csv` files. Safe to delete or regenerate for research; does not affect trading.

### Defect 6 — Tower 2 VIX cron did not log for 2026-04-20 22:00 — **OPEN, DIAGNOSE BEFORE TRADING**

Tower 2's `vix_update.log` last entry is 2026-04-17 (Friday). Saturday/Sunday are non-firing days. Monday 2026-04-20 should have fired — `last -x` confirms Tower 2 booted Mon 13:14 and has been running since, so the tower was up at 22:00. No log line was produced.

Hypothesis: cron service not started post-reboot, or `set -e` in the script caused a silent early exit before the final `echo`. Diagnostic:

```fish
systemctl is-active cron                                       # on Tower 2
bash -x ~/captain-system/scripts/update_vix_data.sh            # observe exit point
tail ~/captain-system/logs/vix_update.log                      # confirm subsequent run logs

```

If `cron` is inactive, `sudo systemctl enable --now cron`. Must be resolved before Tuesday 22:00 or the next weekday cron slot, otherwise AIM-04/AIM-11 run on progressively stale VIX data.

## 7. Cron-aware additions for any fresh-install runbook

The original audit did not surface these because it did not investigate host crons. Any fresh-install procedure (Session D or successor) must include:

**Before wipe:**

- Capture current crontab on both towers (`crontab -l > /tmp/cron-$(hostname)-pre.txt`).
- Pause all three crons (`crontab -l | sed 's/^\([^#]\)/#\1/' | crontab -`) to prevent the 2am QuestDB-backup cron or 22:00 VIX cron from firing during the wipe window.
- Pre-flight existence check on all seed source files (`test -f` every required CSV listed in §5). Abort wipe if any missing.

**After full stack up:**

- Restore crontab from the captured file — not from `deploy/install-vix-cron.sh` (see Defect 2).
- Verify VIX log path uses `/home/$(whoami)/captain-system/...` (avoid re-introducing Defect 1).
- `systemctl is-active cron` on both towers; enable if inactive (addresses Defect 6).
- Prime VIX manually (`bash ~/captain-system/scripts/update_vix_data.sh`) and confirm today's row appears in `vix_daily_close.csv`.
- Confirm `~/healthcheck.sh` exists and is executable; confirm `~/backups/` exists and is writable.

**Cross-tower symmetry gate:**

- Diff `crontab -l`, `ls data/`, and `verify_questdb_state.py` output between towers. All seeded D-tables must match row counts exactly; live L-tables may vary. Any D-table divergence is a red flag.

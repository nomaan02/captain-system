## DEDUP Behaviour Notes

### State tables (D01, D02, D05, D12, D25) — DEDUP is effectively a no-op at runtime

All writers for these tables use `now()` for `last_updated` (the designated timestamp),
which generates a unique timestamp on every write. Because the DEDUP key includes
`last_updated`, DEDUP never fires for these tables in normal operation.

**Consequence:** compaction is NOT belt-and-braces for these tables — it is the primary
deduplication mechanism. `CAPTAIN_COMPACTION_ENABLED=true` must remain the default until
at least two weeks of production monitoring with the new canonical DDL confirms the
behaviour is acceptable. Only after that can compaction be disabled.

### D08 TSM state — same situation

Writers use `now()` for `last_updated`. DEDUP UPSERT KEYS(last_updated, account_id)
won't collapse rows in practice. The C-2 fix (read-modify-write in b7_tsm_simulation)
is the correct mitigation — it ensures the LATEST ON row is always the full 32-col row,
regardless of DEDUP behaviour.

### D08 DEDUP key — account_id chosen

Majority of call sites query `LATEST ON last_updated PARTITION BY account_id`.
`migrate_account.py` (now deleted) used `PARTITION BY user_id` — this was
a SELECT query, not tied to the DEDUP key. LATEST ON is independent of DEDUP keys;
it scans the partition by the specified column. No other active call site uses
`PARTITION BY user_id` on D08.
